# Harness eval round 2 (hard tasks), 2026-11-25

Runner and design: [README](README.md). Previous round: [pilot](pilot-2026-11-25.md). Raw data: [`hard-2026-11-25/runs.jsonl`](hard-2026-11-25/runs.jsonl) (54 records as recorded), [`hard-2026-11-25/reruns.jsonl`](hard-2026-11-25/reruns.jsonl) (5 records that replace the runs lost to an API outage), runner report: [`hard-2026-11-25/report.md`](hard-2026-11-25/report.md). Task descriptions and traps: [`bench/eval-tasks-hard/README.md`](../../bench/eval-tasks-hard/README.md). Raw streams are not in git.

## Conclusion

- **Q1, does odd-claude improve outcomes vs plain Claude Code?** No measurable difference, again. After replacing the 5 outage runs with reruns (see Outage), every arm passes every check in every run: 18/18 acceptance and 18/18 regression in `none`, `coord-on` and `coord-off`. The traps did not separate the arms for Opus 5.5. As recorded (outage runs counted as failures) the arms look different (16/18, 17/18, 16/18), but that difference is the outage, not the agents.
- **Ceiling effect again.** The traps are real: the naive overlays pass acceptance and fail the regression or exact-text checks (selfcheck, `bench/eval-tasks-hard/selfcheck.mjs`). The agents avoided them anyway, with and without the plugin. So the tasks were harder in design but not hard enough for this model; the measurement cannot detect an outcome difference in either direction.
- **Q2, does full delegation pay off its token cost?** Not on these tasks. With equal outcomes, `coord-on` cost 70% more than `none` (tokens +148%, wall +95%) and 12% more than `coord-off` (tokens +39%, wall +25%). `coord-off` cost 52% more than `none`. Across the pilot and this round (108 runs) `coord-on` never bought a measured outcome gain.
- Both answers are bounded by n=3 per cell, one model and tasks written by an LLM (see Caveats).

## Outage and reruns

5 runs ended `status: error` ("claude exited 1"): `event-rename.coord-off.2`, `invoice-rounding.{none,coord-on,coord-off}.2`, `text-table.none.2`. All started between 21:17Z and 21:33Z. Their streams end with 10 `api_retry` events (`error: "unknown"`, no HTTP status) followed by a synthetic assistant message: an API or infrastructure outage, not agent behavior. Four of them recorded cost 0 and no tokens; `event-rename.coord-off.2` recorded USD 0.257 and 162k tokens before dying. Their `wall_ms` (191 to 318 s) is retry time.

The parent re-ran exactly those 5 with the same caps and one trial (`reruns.jsonl`, run ids end in `.1`). All 5 finished `ok` and passed both checks. Two views below:

- **Recorded**: the 54 records as written, errors counted as failed runs (pass rate and stats as the runner's `report.md`; cost, tokens and wall stats include the errored runs' recorded values).
- **Effective**: the 5 errored records replaced by the 5 reruns. This is the view that answers Q1 and Q2. The reruns ran later, with a fresh sample of the same task and arm, so they are not paired with the runs they replace.

## Observation: did agents read the repo docs first?

Spot-check of the tool-call order in 6 streams (observation only, not a measured outcome; "docs" is a README or SPEC named in a tool call before the first Edit or Write):

- `text-table` (the prompt points to `docs/SPEC.md`), runs `none.1`, `coord-on.1`, `coord-off.1`: in all three the first command was `git ls-files && cat docs/SPEC.md package.json ...`, then reads of the source files, before any edit. In `coord-on.1` the main session wrote the brief and one subagent (`Implement renderTable with tests`) did the implementation.
- `invoice-rounding`, the trap is documented only in `README.md`: `none.3`, `coord-off.1` (main run) and `coord-off.1` (rerun) named the README in the first command; `none.1` (main run) never did: it read `src/round.js`, `src/invoice.js`, the visible round test and every `round` usage, wrote a half-up rounding fix whose comment says "half up (toward +Infinity), like Math.round", and brute-force checked it before finishing. It passed both checks. `coord-on.1` (main) cat'd every tracked file in one command (so the README was read without being named) and delegated the edit to a subagent.
- `duration-report`: `none.1` and `coord-off.1` named the README in an early command, `coord-on.1` read it as an early `Read` in the main session, before delegating.

So reading docs first was common in every arm, and one plain run reached the correct behavior from the code and the visible tests alone. Not checked: the other ~100 streams, and whether the briefs passed to subagents carried the README constraints in full.

## Caveats

- n=3 per cell, 18 per arm, 6 per task type. With every cell at 100% the data bounds an outcome difference only loosely: the 95% upper bound for a miss rate is about 17% for n=18 per arm (rule of three).
- The 5 outage runs were replaced by reruns (same caps, a different time window, one trial each), so the effective view is a mix of two sessions; the recorded view is kept in the data.
- One main model (Opus 5.5), one CLI version, one prompt per task, nondeterministic runs.
- Engram is absent: odd-claude was measured without its memory.
- Cost is API-equivalent from `total_cost_usd`; auth was a subscription, so no money was billed.
- Tasks were authored by an LLM worker and validated only by selfcheck (shipped fails acceptance, reference passes everything, naive trips at least one hidden check). Task difficulty for a human or a weaker model is unmeasured.
- Pass/fail only; no review of diff quality or test quality. `visible_tests_modified` is not a cheating signal (it also flags added tests).

## Next steps (recommendations, not done)

1. A weaker main model (for example sonnet or haiku as main) where discipline has room to matter; the same tasks may then separate the arms.
2. Longer-horizon tasks: multi-session work, larger repos, ambiguity that needs spec work rather than a read of the README.
3. Measure cost-efficiency explicitly (cost per passing run, or cost per unit of regression risk avoided), not only pass rate.
4. For the human to weigh, not a decision: `coord-on` as the default adds about +70-80% cost without a measured outcome gain across 108 runs on Opus 5.5. Whether to change the default should wait for result 1 or 2, since the benefit may exist only where the main model is weaker or the work is longer.
5. An arm with engram installed, to measure odd-claude with its memory.
