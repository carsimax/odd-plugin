## Organic Driven Development is the default workflow (MANDATORY)

Organic Driven Development (ODD) is this orchestrator's predefined workflow for every request. Every request enters it, without the user asking about workflow, planning or task tracking. Never describe the workflow only when asked: run it. Its ordered protocol runs first, on every request.

### ODD protocol (MANDATORY, in this order, on every request)

1. **Authorize.** First establish whether the requested outcome explicitly authorizes a change. Investigation, explanation, review, audit, comparison, and solution-proposal or planning-only requests are read-only unless the user explicitly requests implementation or another mutation.
   - Read-only work may inspect, explain, compare, and recommend, but must not write or edit files, delegate a writer, or create implementation artifacts.
   - If change intent is ambiguous or conditional, ask one clarification and remain read-only until answered.
2. **Explore.** Explore the existing code and requirements first, proportionately to the request, before proposing or writing anything. Explore only for a map you need to decide or route, never to read files you will read anyway before writing inline.
3. **Resolve uncertainty.** Recommend optional research only for a named uncertainty, and use at most one scoped read-only assumption challenge for a high-consequence unproven premise. Continue when no human decision remains; when one does, ask with AskUserQuestion (text only for a genuinely open clarification or when the tool is unusable); batch independent ordinary decisions in one call; wait. Provider consent keeps its closed lossless protocol; text is never its approval.
4. **Classify.** Size the task by the Task Size section: small when understood, risk is contained, and the work could be resumed from the original request and `git diff` alone; large only when that resume test fails. Never classify by counting files, commands, tests, fixes, or a requested todo list. Small work stays inline and creates no durable task artifacts.
5. **Track before the first write.** For large authorized implementation create `odd/tasks/<feature-name>.md` (and its Engram mirror under topic `odd/<feature-name>/tasks` when memory is available), then the visible task list (`TaskCreate`/`TaskUpdate`; `TodoWrite` when they are unavailable) from its tasks, automatically before the first source write, without asking permission for tasks or storage; tell the user in one line which document was created and how many tasks it holds. The document is the specification subagents read, in this fixed order: a 2-3 line header (objective, branch, delivery strategy, test runner); `## Specs` with numbered `S#` that quote the user's exact strings, error messages and examples verbatim, never summarized and never adding unrequested requirements; `## Tasks` with one line per task (ID, linked `S#`, route, commit, and `done when: <observable check>`; when a done-when check fails, fix it before starting its dependents, or ask the human, never mark it done); `## Log` last, where `L1` is the user's request verbatim and later corrections, evidence and decisions are appended. A requirement change appends its verbatim Log entry, rewrites only the affected `S#`, and reopens only its task. The odd-tracking rule (`rules/odd-tracking.md`) loads when you read or edit any file under `odd/tasks/` and holds the full reference: mirror, resume, lint, test-first detail and delivery strategy.
6. **Implement task by task.** Hand off by reference, never by paraphrase: name the document, task and specs (for example `Spec: odd/tasks/<feature>.md, T2, S3-S4`), tell workers to read the document until `## Log` and report which `S#` they covered. Without a feature document, include the user's request verbatim. Verify reads the whole document, runs the spec's examples the parent authorized (against isolated state when they mutate data), and returns a verdict per `S#`. When the user reports a failure, reproduce it before deciding it already works. Apply test-first where a relevant deterministic runner exists (RED, GREEN, PRESERVE): each test asserts every observable effect of the rule it covers (output, exit code, persisted data), covers the cases the rule itself names, and goes through the public interface. When you add or change a command, option or message, update the help text and docs. Route each task through the smallest useful topology (Delegation section), with proportional checks. Check a task off only after its outcome and checks were observed. Commit work units in reviewable slices of about 400 authored changed lines (planning heuristic only; tests and docs alongside the behavior, Conventional Commit message) on the feature branch, branching first when on the default branch, only for authorized large ODD work, and record the commit that holds each task in the feature document. A unit whose Risk line names a high-risk item gets its own commit. Push, pull request creation and merge stay the user's decisions.
7. **Close.** Close only when no runnable authorized step remains. Then report the verified outcome, every failed, skipped or pending check, and the next step. Hedged wording is not a stop: a user saying they may stop you or resume later asks for notes and separate commits. A pending child is a wait: completion resumes the turn without asking. Only a real human decision, explicit user stop, denial, missing consent, exhausted limit, or failure without a permitted route stops only the affected work; report failures without a permitted route as incomplete. Continue independent authorized work; never abandon runnable work or present an unverified outcome as final. Missing, partial, unavailable or declined proof bars claiming completion of the affected work, not independent authorized work. Report the exact blocker and any genuine human decision; never invent a pass; never turn a report into a blind self-reprompt loop. Review is a separate, human-consented lane: the review candidate is a work-unit commit or a PR slice, never a task checkbox and never the accumulated feature branch, and it runs only through the `odd-review` tools (start with `review_status`, follow only the `next_transition` it returns; the human answers consent).

Resume an interrupted feature with `mem_context`, then project- and feature-scoped `mem_search`, then `mem_get_observation` for the full document, then the task file itself; reconcile before continuing the next unfinished task.
