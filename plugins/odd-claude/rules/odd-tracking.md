# ODD tracking and memory reference

Bind this to the parent (main-thread) session only. It loads when you read or edit a feature document under `odd/`; the always-on `protocol` block holds the minimal layout needed to create one. Apply it for large authorized implementation (its resume test fails); a requested session task list alone needs no durable ODD document or memory mirror.

Memory tools are the Engram memory tools `mem_*`: `mcp__engram__mem_*` (user-level server) or `mcp__plugin_engram_engram__mem_*` (plugin server) (for example `mem_context`, `mem_search`, `mem_get_observation`, `mem_save`, `mem_update`). They are available only when the engram server is connected; never invent availability.

### Organic Driven Development (ODD)

These instructions apply to all development work. Preserve the existing direct/delegated topology and one parent owner; do not introduce an ODD CLI, specialized agent, or execution harness.

#### Authorization and progress

Investigation, explanation, review, comparison, and proposal-only requests remain read-only: no writer, apply, or implementation artifacts. Ambiguous or conditional change intent (unclear whether a change is authorized at all) requires one clarification (`AskUserQuestion`); stop and wait. Hedged delivery wording (the user may stop you, review commits one at a time, or pick the work up later) asks for resumable notes and separate commits, not a stop; complete every authorized task in the current turn unless the user explicitly says to wait. Research findings and automatic execution pace never authorize mutations.

Size every task by the Task Size section; small work creates no durable task artifacts, and file, command, test, fix, or line counts never make it large. For large authorized implementation, automatically create the feature document after exploration, without a task or storage permission prompt. Follow "Feature continuity and the Engram mirror" below for the file and Engram recovery copy, automatic updates, truthful checkoffs, and resume. The parent owns reconciliation; bounded workers receive the document locator, task IDs, linked `S#`, authorized scope and checks, not unrelated authority; they read the document until `## Log` before edits and report which `S#` they covered. A rejected or resumed handoff is repaired and resent intact, never shortened. Reproduce a user-reported failure by running its example first; reading code is not reproduction. Close gate: continue every pending tracked task in the document or task list unless it waits on a launched child; an already-decided denial, missing consent, or exhausted limit applies to that affected work; the user stopped only that work; or a genuine human decision is open. Unrelated runnable authorized work continues while blockers or missing proof are reported.

Use about 400 authored changed lines per ODD task only as a planning heuristic, counting additions plus deletions. Keep the smallest coherent behavior with its tests and docs. This is not a task acceptance criterion, hard cap, counter-trigger, automatic stop, forced split, or review trigger. If the correct clear solution naturally exceeds it, briefly explain why and continue without size-only rework loops. Never delete spaces, blank lines, or comments for cosmetic line savings; never omit tests, minify, add gratuitous abstractions, or split artificially to fit the heuristic. Forward this same advisory-only instruction when delegating tasks to subagents. The delivery budget below reads the accumulated branch, not this per-task heuristic. Existing PR size gates remain unchanged; follow repository policy. A user's line limit is a ceiling, never an exact-count gate; never invent acceptance gates the user did not ask for.

#### Done-when checks and document lint

Every task line in `## Tasks` ends with `done when: <observable check>` (the command or observation that proves it: a test name, a CLI output, a file state). Stop-and-fix: when a task's done-when check fails, fix it before starting a task that depends on it, or ask the human; never mark it done on a failing check.

At closure, run `node "${CLAUDE_PLUGIN_ROOT}/dist/cli/tasks.js"` (read-only, always exit 0; `--json` for machine output). Fix every finding for the feature document you worked on (stale open tasks, done tasks without a Log entry, tasks without `done when`, missing sections) before reporting completion, closing a task only with git or Log evidence (otherwise report the finding); report findings in other documents without editing them.

#### Research depth without a new phase

Step 3 decides when to research, ask, or challenge. Establish the problem, intended outcome, constraints, and current evidence; inspect relevant code. Adapt depth to uncertainty and consequence: no fixed questionnaire or mandatory rounds. The parent owns product decisions; workers return gaps to the parent rather than assuming choices.

When the question needs external evidence, use available authorized documentation/web tools (`WebSearch`, `WebFetch`) and prefer primary sources. Attribute material claims to URLs or code locations; distinguish verified facts, assumptions, contradictions, freshness, and gaps. If tools are unavailable, disclose limitations without inventing access or evidence. If research is declined, continue within authorized scope only where safe without the missing evidence; pause only unsafe decisions dependent on it.

Return concise findings, recommendation, tradeoffs, open questions, and implementation implications. Offer a concise proposal only when a real scope or product decision needs it. Forward these research instructions to an existing fresh general exploration/research worker (`odd-explore`) through the existing delegation mechanism; do not create a specialized agent or create a new workflow. Research remains read-only and requires no new persistence or readiness machinery.

The step 3 assumption challenge is independent and allowed even in a small security-critical change. Name the premise, evidence, and consequence; do not start a debate loop. Deterministic failures need fixes, not model debate.

Before building, validate any consequential premise whose failure would invalidate the approach. Reuse relevant findings from sibling investigations instead of repeating the same exploration; verify only what is stale or materially different. During iteration, run focused checks for the behavior being changed, then run the applicable full suite at closure.

#### Checks and review

Test-first is the harness principle (see "Test-first detail" below) (test or framework presence alone does not establish applicability); forward this policy, the applicable exact runner and commands (when available), and any exception rationale on every implementation delegation, refresh it on resume, and record observed evidence or the reason for fallback in the feature document.

Run applicable functional checks per task; a task-list checkbox never triggers a review cycle. Checklists grant no approval; the review candidate is a work-unit commit or a PR slice, never a checkbox and never the accumulated feature branch. Review is advisory and parent-owned (see protocol step 7).

#### Delivery

Delivery follows work units. At feature-document creation, forecast authored changed lines (additions plus deletions, generated files excluded) from the task list, and keep a running count from work-unit commits. Choose one delivery strategy per feature: `single-pr` (default), `ask-on-risk`, `auto-chain`, or `exception-ok`. Under the default, all work-unit commits stay local and reach GitHub as one pull request when the user asks to publish; no chain menu is asked. Past about 400 authored changed lines (forecast or running count), record the slice boundary in the feature document; apply the chosen strategy only when the user asks to publish (push or PR), never before a local work-unit commit. Local work-unit commits stay separate from publishing. When the user picks `ask-on-risk`, it asks once using the ordered oversized-delivery menu; `auto-chain` asks only for a missing chain strategy and slices automatically with a cached choice. When a choice is needed on either chaining path, offer exactly these three semantic outcomes in order (`AskUserQuestion`):

1. **Feature/tracker branch chain** — `chain_strategy=feature-branch-chain`.
2. **Verified default/main branch chain** — `chain_strategy=stacked-to-main`; verify the destination's default branch rather than assuming its name.
3. **One single PR — least recommended** — `delivery_strategy=single-pr`.

Generate the complete user-facing question and every option label, description, and recommendation marker in the active user's conversation language. Machine strategy tokens remain unchanged and untranslated. These English examples are illustrative and localizable, not mandatory copy.

The third choice overrides the pending chaining path: clear the chain choice as inapplicable and suppress later chain prompts. `single-pr` is not a `chain_strategy` token; do not automatically select `exception-ok`. An oversized single PR adds reviewer load, delays feedback, and couples rollback; least recommended applies only to this menu, not focused ≤400-line PRs. Follow the destination repository's documented contribution/size policy: a `size:exception` label applies only where the destination policy uses it; never add it otherwise, and preserve its maintainer acceptance and protected-label authorization. A single PR needs no tracker, child dependency diagram, or Chain Context. Shape selection does not authorize push, PR creation, or merge. Cache both choices, and record slice boundaries (which commits each PR holds) when chaining; for single PR, the whole-PR scope. Resolve the `work-unit-commits` and `chained-pr` skills by registry name (`/work-unit-commits`, `/chained-pr`), never hardcode their paths.

#### Test-first detail

Apply one default test-first policy to ODD behavior changes: when a relevant runnable deterministic test and a clear expected outcome exist, observe RED before implementation, implement GREEN, then refactor while tests stay green. Write one RED test per requested rule. For every existing command or option the change touches, add one test proving its previous behavior still holds; add no other cases. An existing behavior counts as touched when it shares the code you changed (options, parsers, helpers, validation). Before finishing, run a differential check: for each existing command that shares the code you changed, run it with the new or changed input (for example a new option passed to a sibling subcommand) against the previous code (a copy of the base commit in a `mktemp -d` scratch directory, never committed as a test; committed tests never read git history or a fixed commit) and against your change, and compare stdout, stderr, and exit code; any difference nobody asked for is a regression to fix and pin with a test. Tests or frameworks being present alone do not establish applicability. For passive documentation, unavailable runners, or no meaningful runnable RED, explain the exception and run proportionate functional or structural checks. Keep test scratch state (temporary directories, `HOME`, `TMPDIR`, tool caches) outside the worktree in a `mktemp -d` directory; when it must live inside the worktree, use a path git excludes and remove it before finishing, so no tool cache or scratch path remains in the change. Subagents never delete scratch: they report its exact paths, and the parent removes outside scratch after use, including the paths a worker or verifier reports. Forward the applicable runner, this test discipline, and the evidence or exception to workers; never invent RED/GREEN evidence or a runner.

### Feature continuity and the Engram mirror

For large authorized implementation (Task Size), the parent maintains `odd/tasks/<feature-name>.md` and an Engram recovery copy under topic `odd/<feature-name>/tasks`, scoped to the current project. The feature document is canonical; the Engram mirror and the task list (`TaskCreate`/`TaskUpdate`; `TodoWrite` when they are unavailable) are projections refreshed at task transitions. Use a descriptive filename-safe feature name, reuse the same identity, and never overwrite another feature. Keep one feature document, not a separate plan file or topic. It is the specification subagents read by reference, so keep this fixed order, stable content first and the growing log last:

1. A header of two or three lines: objective, branch, delivery strategy, and test runner.
2. `## Specs`: numbered `S1`..`Sn` requirements, constraints, and acceptance criteria with their checks. Quote the user's exact strings, error messages, commands, and examples verbatim, in the user's language; you may number and order them, but never summarize or reword those fragments. Do not add requirements the user never asked for; mark assumptions as assumptions.
3. `## Tasks`: one line per task, using stable task IDs, with its linked `S#`, route (who writes it), status, and commit identity or RED/GREEN evidence.
4. `## Log`: the logbook. `L1` holds the user's original request verbatim; later user corrections are logged verbatim with their date. Problem analysis, rationale for meaningful accepted changes, verification evidence, progress, and next step go here. Routine corrections stay brief; no exhaustive decision journal.

Mirror the full current document and repository-relative file locator, not only a summary or completion notice. Update the feature document with targeted edits; never rewrite the whole file to change a task line or append a log entry.

Accepted user or verification changes automatically update affected intent and tasks, unlike a process that regenerates every artifact: a requirement change appends its verbatim `## Log` entry, rewrites only the affected `S#`, and reopens only its linked task; preserve valid completed and unrelated work; add genuinely new tasks or reopen invalidated items with a reason, and revise their checks. Findings alone never authorize scope expansion or automatic acceptance. New business scope still requires user authorization. Check off only observed outcomes with applicable proof; record failed, unavailable, skipped, or pending checks honestly. The parent merges bounded worker results rather than replacing the entire feature with one worker's partial view.

Persist local progress first, then mirror through the Engram save tool. Refresh the Engram mirror once per task transition (a task starts, finishes, is blocked, reopened, or dropped) or material plan change, and at close; `## Log` entries and evidence added between those points go to the file only and reach the mirror at the next one. After a successful local update and an explicit, complete save acknowledgement, inspect the changed local task/log lines as needed; do not routinely reread both full copies. These writes are not atomic; never author comparison or reconciliation scripts or gates for them. A missing, partial, truncated, failed, or uncertain acknowledgement requires checking which writes already applied before any retry; never replay an applied write. If the tool reports a payload it cannot preserve, keep the file and mark its mirror pending rather than repeatedly resending the same payload. The file is the source: a mirror that differs from the file just written is refreshed from the file, never a blocker. If Engram is unavailable, preserve local progress and explicitly mark the mirror pending; do not claim persistence succeeded or block unrelated safe work. Resynchronize when available. If a file write is unsafe or unavailable, preserve existing state and report the limitation. Preserve both versions on irreconcilable edits and ask only about the real conflict (`AskUserQuestion`); never silently prefer a newer timestamp.

On resume, use `mem_context`, then project/feature-scoped `mem_search`, and `mem_get_observation` for the full saved document; read the actual task file. Do not infer active work from the newest global memory. Reconcile current requirements, code, and proof before continuing the next unfinished task. Preserve pending mirrors and conflicting edits; a missing copy is not permission to overwrite surviving progress.

At initial implementation or recovery after interruption or context loss, the parent reads both the actual file and full observation, reconciles them, and passes the locator, task IDs, and linked `S#`; workers read the document until `## Log` before edits. Within an intact continuation, reuse the established specs, next task, route, and applicable proof instead of restarting discovery or rebuilding the plan at every task. A progress question does not restart preparation: answer briefly with the concrete change, pending check or blocker, then continue the authorized task. New scope, external edits, stale proof, or missing context require inspecting the affected state before editing. Small work without a document still receives its authorized scope and checks.

The visible task list (the phrasing above) is required for large ODD, not a third authority. After reconciling and writing the durable file and Engram copy, create or rebuild the visible list from the same feature tasks before the first source write; after every task transition and material plan change, update both durable copies and the visible projection in the same turn; clearing the visible list must not delete or replace the durable file or Engram copy. If the projection is unavailable, record that limitation without pretending it is synchronized. When a change of direction makes tasks obsolete, mark them `dropped` in `## Tasks`, append the reason to `## Log`, and project them as `dropped` in the same turn; never mark them `done` or leave them `pending`. A dropped task never satisfies the tasks that depended on it: rework, reorder, or drop those too. When a task waits on something outside the list (a person, another team, an authorization), mark it `blocked` with a note naming what it waits for and the observable condition that unblocks it; return it to `pending` or `in_progress` once that holds, or `dropped` if abandoned. A prerequisite inside the list is ordering, not blocking: add it as a task and keep the dependent one `pending`. Small/read-only work does not acquire an ODD artifact or task list merely because the UI can display tasks.

Memory lifecycle rule (when Engram exposes lifecycle metadata/tooling):

- At session start or before architecture-sensitive work, call the Engram review tool with action `list` for the current project when the tool is available.
- If the review tool is unavailable, do not fail the task. Continue with the Engram context/search tools, and still apply lifecycle metadata from any returned observations when present.
- `active` memories may be used normally.
- `needs_review` memories are stale context, not trusted facts.
- When a retrieved memory is marked `needs_review`, surface that stale context to the user and verify it against current evidence before relying on it.
- Do NOT call the review tool with action `mark_reviewed` automatically. Only call `mark_reviewed` after explicit user confirmation or through a dedicated memory maintenance command.
